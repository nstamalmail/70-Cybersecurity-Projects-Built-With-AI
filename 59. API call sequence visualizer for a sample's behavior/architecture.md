# Architecture: API Call Sequence Visualizer — Sample Behavior (GUI-Based Solution)

**Document Version:** 1.0  
**Author:** Senior Security Developer  
**Target Platform:** Cross-platform Desktop (Windows, Linux, macOS)  
**Core Capability:** Ingest, parse, correlate, and visualize API call sequences from dynamic malware analysis reports (Cuckoo/CAPE) as navigable behavior timelines  
**GUI Stack:** Python 3.10+ / PySide6 (Qt6)  
**Status:** Design Specification

---

## 1. Executive Summary

The **API Call Sequence Visualizer (ACSV)** is a GUI-driven desktop application for malware analysts, DFIR investigators, and threat hunters who need to understand a sample's behavior from dynamic analysis reports. It ingests JSON reports generated by Cuckoo Sandbox or CAPE (the de facto standards for automated malware behavior logging) and transforms the raw sequence of API calls into an interactive, navigable timeline that reveals behavioral patterns, process relationships, and attack progression.

The core challenge this tool addresses is a well-documented one: dynamic analysis reports produce **thousands of API calls per process**, creating "nothing but a list of calling records" that is difficult to interpret, especially for analysts without deep Windows API knowledge . Existing tools either dump raw JSON or present flat tables that fail to convey temporal relationships, process ancestry, or behavioral intent.

The tool is designed around four principles:

1. **Process-centric, not call-centric** — organize by process tree first; API calls are attributes of process behavior.
2. **Temporal context matters** — the *order* of API calls is as important as the calls themselves; sequences reveal intent (e.g., `VirtualAllocEx` → `WriteProcessMemory` → `CreateRemoteThread` = injection).
3. **Filter noise, surface signals** — aggregate repetitive calls (loops, polling) and highlight high-value API categories (process, memory, network, registry, file).
4. **Analyst-first drilling** — every visual element is clickable; every API call shows full arguments, return value, and contextual relationships.

## 3. Component Breakdown

### 3.1 Presentation Layer (PySide6 / Qt6)

| Widget | Responsibility |
|---|---|
| `ReportLoaderView` | Drag/drop Cuckoo/CAPE JSON reports. Auto-detect format (Cuckoo v1/v2, CAPE). Display report metadata: sample hash, analysis duration, threat score, signatures triggered . |
| `ProcessTreeView` | **Primary navigation.** Hierarchical process tree from the report's `behavior.processtree` . Click a process to filter all other views. Show process name, PID, PPID, first-seen timestamp. Color-code by suspicious API usage. |
| `BehaviorTimelineView` | **Primary visualization.** Horizontal timeline per process (or aggregated across processes). Each API call is a colored marker positioned by timestamp. Marker color = API category (file, registry, network, process, memory, sync). Zoomable; hover shows call name; click opens detail pane. |
| `ApiCallDetailView` | Full detail of selected API call: timestamp, process, API name, category, arguments (name/value pairs), return value, status (SUCCESS/FAILURE), repeated count . |
| `SequenceMatcherView` | Define and search for API call *sequences* (n-gram patterns). E.g., "VirtualAllocEx followed by WriteProcessMemory within 5 seconds". Highlight matches on timeline. |
| `HeatmapView` | Aggregate view: API call frequency by category per process. Identifies "hot" processes and behavioral concentrations. |
| `FilterBar` | Filter by: process, API category, API name (regex), time range, status (SUCCESS/FAILURE), argument keyword. |
| `IOCSummaryView` | Extracted IOCs from behavior logs: files written, registry keys modified, mutexes created, network endpoints contacted . |
| `EvidencePane` | Right-side detail pane showing raw JSON for the selected element; copy-to-clipboard; cross-reference to other views. |
| `ConsoleView` | Live log tail; parse warnings; filter errors. |

**Key UI Patterns**
- **Process tree + timeline layout**: process tree on left (fixed width ~300px), timeline on right (fills remaining space). Selecting a process filters the timeline.
- **Marker aggregation**: at low zoom levels, markers aggregate into density indicators; zoom in to see individual calls.
- **Click-to-drill**: click marker → detail pane; right-click → context menu (filter to this API, filter to this process, search for similar sequences).
- **Color coding**: consistent category colors across all views (process=red, memory=orange, network=blue, file=green, registry=purple, sync=gray).
- **Virtualized rendering**: timeline uses a custom `QGraphicsScene` with level-of-detail (LOD) aggregation to handle 100k+ API calls.

### 3.2 Orchestration Layer

**Ingest Queue**
- Priority queue for report parsing.
- Task = `(task_id, report_path, case_id)`.
- Persisted to SQLite for crash recovery.

**Sequence Analyzer**
- Parses the report's `behavior.processes[].calls[]` array .
- Normalizes each call into a canonical `ApiCall` record.
- Handles Cuckoo/CAPE differences: CAPE uses BSON logs with compression and loop detection ; Cuckoo uses JSON.

**Filter Engine**
- Applies user filters to the call set; returns a filtered iterator.
- Supports: process ID, API name (exact/regex), category, time range, status, argument substring.

**Scheduler**
- Parsing: parallelized across processes (each process's call log is independent).
- Sequence matching: parallelized across patterns.
- Timeline rendering: main-thread only (Qt graphics).

### 3.3 Report Parser Layer

**Supported formats**

| Format | Source | Key Fields |
|---|---|---|
| **Cuckoo JSON** | `report.json` | `behavior.processes[].calls[]`, `behavior.processtree`, `behavior.summary`  |
| **CAPE JSON** | `report.json` (REST API) | Same structure + CAPE-specific payloads/configs  |
| **CAPE BSON** | Raw `bson` logs | Binary format parsed by `BsonParser`; handles architecture detection and type conversion  |

**Call record normalization**

```python
@dataclass
class ApiCall:
    call_id: str                    # ULID
    process_id: int
    process_name: str
    parent_pid: int | None
    timestamp: float                # seconds from analysis start
    category: str                   # 'file', 'registry', 'network', 'process', 'memory', 'sync', 'system', 'ui'
    api: str                        # 'CreateFileW', 'RegSetValueExW', ...
    status: str                     # 'SUCCESS', 'FAILURE'
    return_value: str | None
    repeated: int                   # consecutive repeat count 
    arguments: list[ApiArgument]
    raw: dict                       # original JSON/parsed BSON

@dataclass
class ApiArgument:
    name: str
    value: str
```

**Process tree reconstruction**
- From `behavior.processtree` .
- Fallback: derive from `behavior.processes[].parent_id` if tree missing.

**Loop detection**
- Detect repeated API calls (e.g., 1000x `ReadFile` in a loop).
- Collapse consecutive identical calls into a single aggregated marker with `repeated: N` .
- CAPE's `CuckooBsonCompressor` uses N-Gram algorithm for this .

### 3.4 Sequence Pattern Matcher

**Purpose**: Find behavioral *sequences* that reveal intent, not just individual calls.

**Pattern definition**
```yaml
pattern:
  name: "Process Injection"
  id: "pat-process-injection"
  severity: "high"
  sequence:
    - api: "VirtualAllocEx"
      category: "memory"
    - api: "WriteProcessMemory"
      category: "memory"
      within_seconds: 10
    - api: "CreateRemoteThread"
      category: "process"
      within_seconds: 5
  group_by: [process_id, target_process]
  description: "Classic process injection sequence"
  references:
    - "MITRE T1055"
```

**Matching engine**
- Sliding-window n-gram matching across the call sequence.
- Time constraints between calls (`within_seconds`).
- Process-grouping: match within same process or across related processes.
- Argument-aware matching (e.g., target process ID in `WriteProcessMemory` arguments).

**Built-in patterns**
| Pattern | Sequence | Severity |
|---|---|---|
| **Process Injection** | `VirtualAllocEx` → `WriteProcessMemory` → `CreateRemoteThread` | High |
| **Credential Access** | `OpenProcess(lsass)` → `ReadProcessMemory` | Critical |
| **Persistence (Run Key)** | `RegOpenKeyEx` → `RegSetValueEx` with "Run" | High |
| **Dropper** | `CreateFile` → `WriteFile` → `CreateProcess` | Medium |
| **C2 Beacon** | `InternetOpen` → `InternetConnect` → `HttpSendRequest` | High |
| **Anti-Debug** | `IsDebuggerPresent` → conditional branch | Medium |
| **Ransomware Behavior** | `FindFirstFile` → `CreateFile` → `WriteFile` (loop) | Critical |

**Custom patterns**
- User-defined YAML patterns in `patterns/` directory.
- Import/export patterns.
- Match results highlighted on timeline.

### 3.5 API Categorizer

**Category mapping**
- Based on Cuckoo/CAPE's own categorization (the `category` field in each call) .
- Fallback: heuristic classification by API name prefix (e.g., `Reg*` → registry, `CreateFile*`/`ReadFile` → file, `Internet*`/`WinHttp*` → network).

**Category colors**
| Category | Color |
|---|---|
| process | Red |
| memory | Orange |
| file | Green |
| registry | Purple |
| network | Blue |
| sync | Gray |
| system | Brown |
| ui | Cyan |

### 3.6 Storage Layer

**Case Directory Layout**
```
cases/<case_id>/
├── case.db                      # SQLite: reports, processes, api_calls, matches
├── manifest.json                # Case metadata
├── reports/
│   └── <report_id>/             # Parsed report cache
│       ├── parsed.jsonl         # Normalized API calls
│       └── process_tree.json
├── patterns/
│   └── matches.jsonl            # Sequence match results
└── logs/
    └── session.log
```

**SQLite Schema (abridged)**
```sql
CREATE TABLE reports (
  id TEXT PRIMARY KEY, case_id TEXT,
  source_path TEXT, format TEXT,  -- 'cuckoo', 'cape'
  sample_sha256 TEXT, analysis_duration REAL,
  threat_score REAL, signatures_json TEXT,
  parsed_at TIMESTAMP
);
CREATE TABLE processes (
  id INTEGER PRIMARY KEY, report_id TEXT,
  process_id INTEGER, parent_pid INTEGER,
  process_name TEXT, first_seen REAL,
  FOREIGN KEY(report_id) REFERENCES reports(id)
);
CREATE TABLE api_calls (
  id INTEGER PRIMARY KEY, report_id TEXT, process_id INTEGER,
  timestamp REAL, category TEXT, api TEXT,
  status TEXT, return_value TEXT, repeated INTEGER,
  arguments_json TEXT
);
CREATE INDEX idx_calls_report ON api_calls(report_id);
CREATE INDEX idx_calls_process ON api_calls(process_id);
CREATE INDEX idx_calls_category ON api_calls(category);
CREATE INDEX idx_calls_api ON api_calls(api);
CREATE INDEX idx_calls_ts ON api_calls(timestamp);
CREATE TABLE pattern_matches (
  id INTEGER PRIMARY KEY, report_id TEXT, pattern_id TEXT,
  process_id INTEGER, start_ts REAL, end_ts REAL,
  call_ids_json TEXT, severity TEXT
);
```

## 4. Threading & Concurrency Model

```
Main Thread (Qt)
  ├── UI events, timeline rendering, detail pane updates
  └── EventBus.emit(signal) ──► Qt QueuedConnection ──► UI slots

Parse Pool (QThreadPool, N workers)
  ├── Report parser threads   (parallel across processes)
  ├── Sequence matcher        (parallel across patterns)
  └── IOC extractor           (parallel across call categories)

Writer Thread (serial)
  └── SQLite WAL writes (batched, 500 calls per transaction)
```

**Rules**
- Report JSON can be large (100MB+); parse streaming, not full-load.
- CAPE BSON logs: parse incrementally with `mmap` where possible .
- SQLite in WAL mode; single writer; batch inserts for performance.
- Timeline rendering on main thread only; LOD aggregation keeps frame rate ≥ 60fps.
- Cancellation: cooperative `threading.Event` checked between process batches.

## 5. Workflow: End-to-End User Journey

1. **Load Report** → drag/drop Cuckoo/CAPE `report.json`; auto-detect format; display sample hash, duration, threat score, triggered signatures .
2. **Parse** → extract process tree, API calls, summaries (files, registry, mutexes) .
3. **Normalize** → convert to `ApiCall` records; assign categories; detect and collapse loops.
4. **Build Process Tree** → reconstruct hierarchy; display in tree view.
5. **Apply Patterns** → run built-in and custom sequence patterns; highlight matches.
6. **Visualize** → timeline view shows API calls colored by category, positioned by time.
7. **Triage** → filter by process, category, API, time range; drill into detail pane.
8. **Investigate Sequences** → search for behavioral patterns; click match to see supporting calls.
9. **Extract IOCs** → review files, registry, mutexes, network endpoints.
10. **Export** → timeline report (HTML/PDF/CSV), IOC list (JSON/STIX).

## 6. Security Considerations

| Concern | Mitigation |
|---|---|
| Malicious report (parser exploit) | Parser runs in subprocess with resource limits; fuzz-tested; no `eval`. |
| Malicious API arguments (injection) | Arguments displayed as text; never executed; Qt HTML escaping. |
| Report data sensitivity | Reports contain sample behavior; case directories encrypted at rest (optional). |
| Pattern injection (YAML) | YAML is data, not code; schema-validated; no code execution. |
| Large report DoS | Configurable max report size; streaming parse; memory bounds. |
| Path traversal from report paths | Sanitize filenames; never use report-provided names for file paths. |
| IOC leakage in exports | Redaction profile for external sharing; audit export actions. |

## 13. Open Questions / Decisions Pending

1. **Cuckoo vs CAPE priority** — CAPE is the actively maintained successor . Recommend: CAPE primary, Cuckoo compatibility.
2. **BSON parsing complexity** — CAPE's BSON format requires architecture detection and type converters . Recommend: implement in P5; JSON-first for P0-P4.
3. **Pattern DSL richness** — start with simple sequence + time constraints; expand to argument-aware matching in v2.
4. **Live sandbox integration** — optional REST API polling for live reports . Recommend: v2 feature.
5. **Machine learning sequence analysis** — research direction (n-gram tf-idf, GRU) . Recommend: out of scope v1; design pattern library to support future ML integration.
6. **Timeline rendering library** — `QGraphicsScene` vs `pyqtgraph` vs custom `QWidget`. Recommend: `QGraphicsScene` for flexibility.

## 14. Glossary

- **API Call Sequence** — ordered list of Windows API functions invoked by a process during execution.
- **Cuckoo Sandbox** — open-source automated malware analysis system .
- **CAPE** — Cuckoo fork with enhanced config extraction and payload analysis .
- **BSON** — Binary JSON; CAPE's behavior log format .
- **Process Tree** — hierarchical parent-child relationship of processes.
- **Loop Detection** — collapsing consecutive repeated API calls into a single entry with a count .
- **N-gram** — contiguous sequence of N items (API calls) from a given sample .
- **Sequence Pattern** — defined behavioral sequence (e.g., injection chain) matched against the call log.
- **LOD** — Level of Detail; rendering optimization for large datasets.
- **IOC** — Indicator of Compromise.
- **API Category** — grouping of APIs by function (file, registry, network, process, memory).
